# Фаза: этап Э$ARGUMENTS

Работаем над этапом Э$ARGUMENTS из раздела 10 @plan.md. Требования — @spec.md.
Если номер не указан или такого этапа нет — спроси и остановись.

Команды проверки (все четыре, всегда вместе, с полным выводом):

```
npx vitest run
npx tsc --noEmit
npx eslint .
npm run build
```

Шаги строго по порядку. Не перескакивай, не объединяй.

## Шаг 1. План

Код не писать.

1. Прочитай описание этапа в разделе 10 plan.md и всё, на что он ссылается: команды
   (раздел 7), эндпоинты (раздел 5), решения D-*, раздел 8 (таблица ошибок),
   раздел 9 (перечень тестов), релевантные FR, NFR и критерии приёмки из spec.md.
2. Сверь каждый эндпоинт, поле и код ошибки этапа с документацией Bybit V5.
   Расхождение с планом — вынести отдельным пунктом, не додумывать.
3. Составь таблицу проверяемых утверждений:

   | # | Утверждение | Источник (FR/D/критерий/раздел) | Тест (файл > имя) |

   Каждое утверждение — одно проверяемое свойство поведения, а не «модуль написан».
4. Отдельным списком — граничные случаи: пустые ответы, пагинация на границе,
   отказы API из таблицы раздела 8, отсутствие данных для расчёта (NFR-3: пустое
   значение с причиной), утечка ключа в ошибках (D-10).
5. Отдельным списком — что из референса собираешься взять, и что именно.

Покажи всё пользователю и **остановись до подтверждения**.

## Шаг 2. Тесты вперёд

1. Напиши тесты строго по утверждённому списку. Реализацию не писать —
   только минимальные заглушки сигнатур, чтобы проходил `tsc`.
2. Только фикстуры реальных ответов API, без сети. Фикстуру брать из примера
   ответа в документации Bybit V5 и указывать источник в шапке файла.
3. Эталонные значения не вычислять своей реализацией. Считать независимо (вручную,
   из документации, из фикстуры) и для каждой константы показать пользователю,
   откуда она взялась.
4. Запусти `npx vitest run` — все новые тесты должны упасть по правильной причине
   (не по ошибке импорта или синтаксиса). Покажи вывод.
5. Предложи пользователю закоммитить падающие тесты отдельным коммитом.

## Шаг 3. Реализация

1. Пиши реализацию до зелёного. Тесты из шага 2 не менять. Если тест кажется
   неверным — остановись и скажи пользователю, не правь его.
2. После каждого прогона показывай вывод всех четырёх команд проверки.
3. Никаких skip/todo, подавления ошибок, `any` ради тишины линтера.
4. Жёсткие ограничения из CLAUDE.md (только GET, ключ не утекает, NFR-3) — на
   каждом шаге.

Шаг завершён, только когда все четыре команды зелёные.

## Шаг 4. Ревью

Запусти субагента (Agent, general-purpose) с заданием:

> Отревьюй изменения этапа Э$ARGUMENTS против plan.md (раздел 10, этап Э$ARGUMENTS
> и связанные разделы) и релевантных критериев приёмки spec.md. Список
> утверждений и граничных случаев: <вставить утверждённый список из шага 1>.
> Проверь: каждое утверждение реализовано и покрыто тестом; граничные случаи
> покрыты; ничего вне этапа не изменено; ключ и секрет не попадают в вывод, логи
> и ошибки; расчётные значения отделены от сырых и при невозможности расчёта
> пусты с причиной; нет не-GET запросов. Сообщай только пробелы, влияющие на
> корректность или требования. Стилистику не упоминать. Для каждого пробела:
> файл:строка, что не так, какое требование нарушено.

Покажи пользователю итог ревью. Реальные пробелы — исправить (через шаг 3, с
выводом четырёх команд); спорные — вынести на решение пользователя.

## Шаг 5. Завершение

1. Финальный вывод всех четырёх команд проверки.
2. Предложи коммит с сообщением вида `Э$ARGUMENTS: <суть>` и списком файлов.
3. Сверка перед `/clear`: всё важное из разговора должно жить в файлах, а не только
   в контексте. Пройди по разговору и найди то, что не записано:
   - находки по живым данным и документации для следующих этапов — в plan.md,
     раздел 10, под нужный этап;
   - решения пользователя, меняющие требования, — в spec.md (с датой);
   - отложенные мелочи и открытые вопросы — в plan.md, раздел 10а;
   - факты о пользователе и окружении, полезные в любой сессии, — в память.
   Проверь `git status`: всё закоммичено. Покажи пользователю короткий список, что
   дописано и куда, и закоммить дописанное.
4. Только после сверки напомни пользователю сделать `/clear` перед следующим этапом.
